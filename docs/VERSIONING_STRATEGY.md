# Versioning Strategy

How formulas in this tap are named, versioned, and updated.

## TL;DR

- Formulas are named for their **purpose/identity**, not with a homebrew-core-style
  `@X.Y` + `Aliases/` scheme.
- A formula's version lives in its `.rb` file (`url` + `sha256`). `brew` installs from
  **HEAD of the default branch**, so there are **no git tags, no `CHANGELOG`, and no
  `Aliases/` directory** — the formula file is the version of record and `git log` +
  closed PRs are the changelog.
- Patch updates are edited **in place** (no file rename).
- Changes ship via **issue → branch → PR (`Closes #n`) → squash-merge**.

## The formulas

| Formula | Kind | Versioned by | Update model |
|---|---|---|---|
| `openssl-ruby` | source build, keg-only | `url` / `sha256` in the `.rb` | manual in-place bump within the OpenSSL 3.5 LTS line |
| `ca-certificates` | source/data (Mozilla CA bundle) | `url` / `sha256` in the `.rb` | manual in-place bump when Mozilla ships a new bundle |
| `engineer` | prebuilt binary (cargo-dist) | `version` + per-arch `url` / `sha256` | regenerated and pushed by cargo-dist at release; **not hand-edited** |

## Naming: purpose-based, not `@X.Y` + aliases

homebrew-core names versioned formulas like `openssl@3.5.rb` (class `OpensslAT35`) and
provides convenience aliases such as `openssl@3 → openssl@3.5.rb`. **This tap deliberately
does not do that for its OpenSSL**, and the difference is load-bearing — do not "restore
conventions" by renaming `openssl-ruby` back to `openssl@3.5` or adding an `Aliases/`
directory.

Why `openssl-ruby`, not `openssl@3.5`:

- **ruby-build auto-detection.** ruby-build (used by `rbenv`/`mise`/`asdf` and driven by
  `RUBY_CONFIGURE_OPTS`) auto-detects any Homebrew formula whose name matches `^openssl@`
  and may silently link Ruby against it. A purpose-named `openssl-ruby` is invisible to
  that heuristic, so the OpenSSL used to build Ruby is only ever the one you point at
  explicitly with `--with-openssl-dir=$(brew --prefix openssl-ruby)`.
- **Single, explicit purpose.** The formula exists for exactly one job — an isolated,
  version-controlled OpenSSL for building Ruby — so a descriptive name states intent
  better than a version alias.
- **Keg-only, unconditionally.** It is keg-only via a *string* reason (not
  `:versioned_formula`) so it is never symlinked into `HOMEBREW_PREFIX`, where it would
  shadow the system `openssl@3`. See the comment on `keg_only` in
  `Formula/openssl-ruby.rb`.

This naming — and the removal of the `Aliases/` directory — was decided in commit
`956df93` (rename `openssl@3.5 → openssl-ruby`). The full rationale, including the
OpenSSL 3.6.0 CRL incident that motivated an isolated OpenSSL, is in
[OPENSSL_RUBY_INCIDENT.md](./OPENSSL_RUBY_INCIDENT.md).

> **When the `@X.Y` + alias convention _is_ appropriate.** If you ever add a
> *general-purpose* pinned formula (say a `postgresql@17`), the homebrew-core
> `@MAJOR.MINOR` filename + alias convention is a reasonable choice — track patches inside
> the file, alias the major version for convenience. It is only wrong for the
> Ruby-isolation case above, where matching `^openssl@` is exactly what we must avoid.

## Updating `openssl-ruby` (track a minor series in place)

`openssl-ruby` pins the OpenSSL **3.5 LTS** series (supported through 2030-04-08). Pinning a
*minor* series means tracking its **patches**, not freezing one release — a stale pin is a
security liability, not stability.

**Patch bump (e.g. 3.5.7 → 3.5.8), in place — no rename:**

1. Edit `Formula/openssl-ruby.rb`: update `url`, `mirror`, `sha256`, and the `# Version:`
   line + patch-bump note in the header comment.
2. Verify the checksum against upstream's published `openssl-<ver>.tar.gz.sha256` before
   committing.
3. Ship via the standard flow (below). CI build-tests it from source on `macos-14`.

**Moving to a new minor series (e.g. a future 3.x LTS):** treat it as a deliberate
migration, not a mechanical bump — update `url`/`sha256`, refresh the header's LTS-window
note, and re-test Ruby against it. There is no alias to repoint; the formula name and
`openssldir` (`etc/openssl-ruby`) stay the same so existing Ruby builds keep resolving to
the same path.

## Updating `ca-certificates`

A plain source/data formula (the Mozilla CA bundle, date-versioned upstream). Bump `url` +
`sha256` in place when a new bundle is released; no rename, no alias.

## `engineer` (cargo-dist binary formula)

`engineer` ships **prebuilt release binaries** per architecture (no source build). Its
`version` and per-arch `url`/`sha256` are generated by
[cargo-dist](https://opensource.axo.dev/cargo-dist/) at release time and pushed to the tap
automatically — **do not hand-edit it**. cargo-dist emits a `BINARY_ALIASES` constant in
every formula it generates; CI uses that marker to skip the source-build audit/install for
these formulas (see `.github/workflows/tests.yml`).

## Shipping changes

All changes to this tap follow: **GitHub issue → feature branch → PR (`Closes #n`) →
squash-merge → delete branch.** There are intentionally **no git tags and no
`CHANGELOG.md`**: `brew` resolves a formula's version from the `.rb` file at HEAD of the
default branch and never reads tags on the tap repo, so tagging the tap adds no functional
value (homebrew-core doesn't tag either). The formula file is the version of record.

Docs-only PRs run no CI (the `Formula Tests` workflow is path-filtered to `Formula/**`) and
merge cleanly; formula PRs are build-tested on `macos-14`.
